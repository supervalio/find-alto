## Технические вопросы

### Q: Почему выбрал именно эти технологии?

**Ответ (40 сек):**
Next.js 16 — потому что App Router даёт серверные компоненты и файловую маршрутизацию «из коробки». Не нужно настраивать роутинг вручную. TypeScript — чтобы ловить ошибки на этапе написания кода, а не в продакшене. Tailwind CSS 4 — кастомная дизайн-система умещается в 14 строк `globals.css`, без тонны CSS-файлов. Supabase вместо своего сервера — потому что управляемый PostgreSQL с REST API и файловым хранилищем: ноль DevOps, сразу продакшен. Drizzle ORM — типы из схемы БД автоматически подхватываются TypeScript, нельзя написать запрос с несуществующей колонкой.

**Пример из кода:** `src/db/schema.ts` — 7 таблиц описаны в Drizzle, и TypeScript сам проверяет все запросы.

**Навык:** Работа с современным full-stack стеком (Next.js + TypeScript + PostgreSQL).

### Q: Как работает загрузка фото?

**Ответ (30 сек):**
Два пути. В админке — компонент `PhotoUpload.tsx` с drag & drop. Пользователь перетаскивает файл, видит превью. При сохранении формы файл уходит на `/api/upload`. API проверяет: это точно изображение? Размер не больше 10 МБ? Расширение из белого списка? Если всё ок — загружает в Supabase Storage bucket `uploads`. Обратно приходит публичный URL, он сохраняется в базе.

На публичных страницах — фото грузятся через `<img>` с `loading="lazy"`, без next/image потому что URL динамические (приходят из Supabase).

**Пример из кода:** `src/components/PhotoUpload.tsx` + `src/app/api/upload/route.ts`.

**Навык:** Работа с файловым хранилищем, валидация на сервере.

### Q: Какие проблемы возникли при разработке и как решил?

**Ответ (50 сек):**
Три главные. Первая — **Vercel build падал с ошибкой**. Причина: `@neondatabase/serverless` пытался загрузить нативные зависимости на этапе сборки статических страниц. Решение: ленивый `await import()` — драйвер загружается только при первом реальном запросе, Vercel до него не добирается.

Вторая — **админ-панель висла на /admin**. Причина: старый драйвер `neon-serverless` несовместим с Supabase. Решение: миграция на `postgres-js` + `drizzle-orm/postgres-js`.

Третья — **на главной показывалась только Армения вместо 4 стран**. Supabase возвращал одну страну, и код перезаписывал seed-данные. Решение: merge DB + seed — то, чего нет в базе, докидывается из seed-файла.

**Пример из кода:** `src/db/index.ts` (ленивая инициализация), `src/app/page.tsx` (merge-логика).

**Навык:** Дебаггинг продакшен-проблем, graceful degradation.

## Архитектурные вопросы

### Q: Почему такая архитектура? Почему гибридная загрузка Supabase + Seed?

**Ответ (40 сек):**
Это даёт **устойчивость**. Публичные страницы сначала пробуют Supabase — живую базу. Если соединение рвётся или переменные окружения не заданы — страница прозрачно переключается на seed-данные. Пользователь не видит разницы.

Плюс **graceful degradation**: Supabase-клиент и Drizzle-подключение при отсутствии конфигурации возвращают Proxy-объекты. Они не крашат приложение, а отдают `{ data: null, error: "not configured" }`. Это позволяет запустить `npm run dev` без `.env.local` и сразу увидеть сайт с тестовыми данными.

**Пример из кода:** `src/lib/supabase.ts` — функция `createNoopClient()` возвращает цепочку прокси.

**Навык:** Проектирование отказоустойчивых систем, defensive programming.

### Q: Как приложение масштабируется?

**Ответ (30 сек):**
Сейчас 4 страны, 4 дизайнера. Что будет при 50 странах и 500 дизайнерах?

- **Статические страницы** (`/about`, `/countries`) кэшируются на CDN Vercel — нагрузка околонулевая
- **Динамические роуты** (`/[country]`, `/designer/[slug]`) рендерятся на сервере по запросу, но Vercel автоматически добавляет ISR-кэш
- **База данных** — Supabase растёт от бесплатного тира до Pro плана. 500 дизайнеров × 10 вещей = 5000 строк в items — это ничто для PostgreSQL
- **Фото** — Supabase Storage с CDN, раздача не нагружает сервер

При росте трафика: добавить Redis для кэширования частых запросов (например, список стран на главной), перейти на Supabase Pro, подключить Cloudflare.

**Навык:** Понимание масштабирования web-приложений.

### Q: Почему админ-панель без аутентификации?

**Ответ (20 сек):**
Осознанное решение для раннего этапа. Контент-менеджеру не нужно регистрироваться и помнить пароль — он просто заходит по URL. Безопасность компенсируется RLS-политиками Supabase: на уровне базы настроено, кто может читать и писать. На более позднем этапе добавлю простой JWT-логин.

**Навык:** Продуктовое мышление — баланс между безопасностью и скоростью разработки.

## Процесс разработки

### Q: Как использовал AI-агентов (Zed, CodeWhale, GSD)?

**Ответ (50 сек):**
Процесс построен вокруг **5 ролей-агентов**:

- **Team Lead** — оркестрация: декомпозиция задач из Roadmap, назначение агентов, приёмка результатов, коммиты
- **Frontend Developer** — UI, компоненты, стили, вёрстка
- **Backend Developer** — API, база данных, миграции, эндпоинты
- **QA Tester** — тестирование, поиск багов, проверка критериев
- **Security Reviewer** — аудит безопасности, quality gate

Работа по **GSD-фазам**: 6 фаз, каждая с конкретными задачами. Фаза считается завершённой когда все задачи имеют статус ✅.

**CodeWhale** хранит контекст проекта в `.codewhale/` и `.planning/`. **DeepSeek** — модель для генерации кода и анализа.

Я выступаю как **Product Owner**: ставлю задачу → агенты выполняют → я принимаю результат. Это позволило за 2 месяца пройти от идеи до деплоя.

**Пример:** Фаза 1 (Foundation) — 17 задач, все закрыты за 4 сессии. Фаза 5 (Infrastructure) — миграция SQLite→Supabase, настройка RLS, Vercel deploy.

**Навык:** Управление AI-командой, декомпозиция, делегирование.

### Q: Как организовал работу?

**Ответ (30 сек):**
Три слоя планирования:

1. **`.planning/ROADMAP.md`** — 6 фаз, каждая с нумерованными задачами и статусом
2. **`.planning/REQUIREMENTS.md`** — 28 требований с ID (GEO-01, DSGN-01...) — это acceptance criteria
3. **`.planning/HANDOFF.md`** — handoff-файл между сессиями: что сделано, текущий блокер, что дальше

Рабочий процесс: открываю HANDOFF → вижу контекст → беру следующую задачу из Roadmap → декомпозирую → делегирую агентам → принимаю → коммичу → обновляю статус.

Коммиты atomic: одна задача = один коммит с понятным сообщением (`fix:`, `feat:`, `refactor:`).

**Навык:** Управление проектом, документация, дисциплина коммитов.

### Q: Что бы сделал иначе?

**Ответ (30 сек):**
Три вещи:

1. **Дизайн-систему зафиксировал бы жёстче с первого дня.** Мы прошли 4 итерации палитры: тёплая → холодная → зелёный акцент → финальная. Каждая требовала рефакторинга. Если бы сразу зафиксировали в `globals.css` и не трогали — сэкономили бы неделю.

2. **Не использовал бы Drizzle с Neon-драйвером для Supabase.** Это очевидная несовместимость, которая всплыла только на Vercel. Надо было сразу брать `postgres-js`.

3. **Сразу настроил бы CI/CD.** Первые 2 недели деплоил вручную. Vercel + GitHub Actions с авто-деплоем при пуше сэкономили бы кучу времени.

**Навык:** Рефлексия, извлечение уроков из ошибок.
